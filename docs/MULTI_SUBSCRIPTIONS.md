# Несколько подписок в окружении MOX

Требование от 10 сентября 2026: окружение хранит две и более отдельные авторизации, выдаёт персональные ключи сотрудникам и предоставляет им доступ через настольный Codex.

В этой версии реализован интерактивный прототип управления и проверки правил. Реальные аккаунты OpenAI не подключены.

## Состав минимальной серверной реализации

Один сервис MOX с панелью администратора, API для настольного Codex, базой ключей и правил доступа. Рядом — отдельное подключение к провайдеру для каждой подписки. Каждый такой адаптер владеет своей авторизацией и обновляет только её.

Для начальной версии достаточно одной базы SQLite и отдельных защищённых каталогов авторизации. Отдельные контейнеры нужны, если требуется более строгая изоляция. Сам движок, инструменты и рабочие файлы сотрудника остаются в настольном Codex.

| Сущность | Что хранится |
| --- | --- |
| Окружение | Идентификатор компании, адрес шлюза, правила администраторов |
| Подключение подписки | ID, ID аккаунта и workspace, название, ссылка на секрет, авторизация, доступность, административная пауза |
| Сотрудник | ID, имя, почта, разрешённые ID подключений |
| Ключ MOX | Хеш случайного ключа, сотрудник, окружение, статус, дата выдачи и отзыва |
| Чат | Сотрудник, окружение, стабильный ID чата клиента, закреплённое подключение |
| Запрос | Чат, подключение, результат допуска, состояние выполнения, идентификатор попытки |

Полный ключ MOX показывается один раз. Авторизация подписок не передаётся сотрудникам и не включается в открытый репозиторий.

## Разделение авторизаций

Codex документирует хранение авторизации внутри CODEX_HOME при cli_auth_credentials_store = "file"; эта переменная также задаёт корень конфигурации, сессий и другого состояния:

- [Credential storage](https://learn.chatgpt.com/docs/auth#credential-storage).
- [Environment variables](https://learn.chatgpt.com/docs/config-file/environment-variables#core-locations).

На сервере каждой подписке нужен свой приватный каталог и свой владелец процесса обновления авторизации. Повторный вход в одном общем каталоге не создаёт отдельного подключения для второй подписки.

Официальная инструкция для доверенной автоматизации требует последовательного использования одной копии auth.json и сохранения обновлённых данных после refresh: [Maintain Codex account auth in CI/CD](https://learn.chatgpt.com/docs/auth/ci-cd-auth). Поэтому у каждого подключения нужен один процесс, владеющий обновлением токенов, и координация запросов к этому подключению.

Это основание для проектирования изоляции. Оно не подтверждает готовый API раздачи личных Pro-подписок сотрудникам. Адаптер подписочного протокола и допустимость конкретного корпоративного использования остаются отдельными вопросами.

## Авторизация подключения

1. Администратор создаёт подключение в MOX.
2. Сервер запускает отдельный процесс входа, связанный только с этим подключением.
3. Администратор проходит официальный вход в выбранный аккаунт.
4. Сервер проверяет фактический ID аккаунта и workspace и сохраняет авторизацию в приватном хранилище этого подключения.
5. Администратор назначает подключение сотрудникам.

При повторном входе ID аккаунта и workspace должны совпасть. Другой аккаунт создаёт новое подключение. Две записи одного аккаунта не должны считаться двумя независимыми подписками или удваивать лимит.

В прототипе вместо официального входа используется явно помеченный шаг «Подтвердить вход (демо)». Проверяется только модель состояний.

## Ключи и права сотрудника

Ключ относится к окружению и сотруднику, а не к одной подписке. Добавление, пауза, отключение или повторная авторизация подключения не меняет ключ.

Подписки назначаются явно. Новый сотрудник видит список выбранных подключений при создании. Добавление третьего подключения не расширяет ранее выданные права; администратор назначает его отдельно.

Отзыв ключа блокирует новые запросы по всем подпискам. Удаление одной подписки из прав блокирует только запросы к ней. Эти операции не удаляют локальную историю сотрудника в настольном Codex.

## Выбор подписки

Для каждого запроса сначала проверяются ключ, окружение и владелец чата.

Для нового чата выбирается подключение, которое одновременно:

- разрешено сотруднику;
- авторизовано;
- не приостановлено администратором;
- доступно в рамках собственных ограничений провайдера.

В прототипе новые чаты каждого сотрудника распределяются по очереди между подходящими подключениями. Выбор закрепляется за чатом до отправки первого запроса.

Для начатого чата повторно проверяются те же условия, но подписка не меняется. Если она недоступна, запрос не направляется. Можно восстановить доступ к ней или явно начать другой новый чат; история и состояние не переносятся автоматически.

Исчерпание лимита одной подписки не обнуляет её ограничения. Повторная авторизация и снятие административной паузы не восстанавливают лимит. В рабочем шлюзе время восстановления и ограничения берутся из данных провайдера; неизвестный остаток не считается ни нулём, ни гарантированной доступностью.

## Неопределённый результат запроса

Если соединение оборвалось после отправки запроса, сервер не должен считать это доказательством невыполнения. Нельзя автоматически повторять такую попытку через другой аккаунт. Нужны запись исходной попытки, состояние «результат неизвестен» и явное дальнейшее действие.

Этот сценарий описан для серверной реализации; в текущем браузерном прототипе сетевых запросов к модели нет.

## Что ещё нужно проверить в рабочем шлюзе

- Реальный вход в две и более подписки, независимое обновление и отзыв их авторизаций.
- Адаптер между Responses-запросами настольного Codex и выбранным подписочным подключением. Запуск codex exec с текстовым запросом сам по себе не заменяет совместимый модельный API.
- Надёжный ID чата в фактических запросах настольного Codex. Один ключ сотрудника не идентифицирует чат: у сотрудника может быть несколько параллельных чатов.
- Привязку previous_response_id и другого серверного состояния к исходному аккаунту; сообщения и ответы разных аккаунтов нельзя смешивать.
- Реальную изоляцию сессий, файлов и учётных данных сотрудников, а также обработку служебных запросов приложения.
- Хранение и отзыв ключей на сервере, авторизацию администратора и проверку доступа на каждом запросе.

Проверка настольного Codex 9 сентября подтвердила собственный адрес провайдера, передачу личного ключа, отображение синтетического ответа и отказ 401 после отзыва. Она не подтверждает перечисленные выше свойства настоящих Pro-подписок.
