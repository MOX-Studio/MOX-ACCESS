# Вход через браузер и расход токенов

Версия прототипа 0.4, 10 сентября 2026. Решение: сотрудник работает в настольном Codex с одним ключом MOX и получает доступ ко всем текущим и будущим подпискам окружения. Сейчас проверяются интерфейс и правила. Настоящего сервера авторизации и модельных запросов нет.

## Сценарий входа в прототипе

«Подключить подписку» → «Войти через OpenAI» → отдельное окно → ожидание результата → подписка в списке.

В `dist/auth-demo.html` находятся только вымышленные аккаунты. Основная страница принимает результат связанной попытки: проверяет окно-отправитель, origin, ID попытки и выданный ей демонстрационный аккаунт. Открытие или закрытие окна не подтверждает вход. Блокировка окна допускает повторное открытие; отмена, истечение ожидания и закрытие главной страницы завершают попытку. После обновления страницы всё демо-состояние сбрасывается.

Повторный вход проверяет прежние ID аккаунта и workspace. Другой аккаунт отклоняется; дубликат существующей подписки не создаётся. Ключи сотрудников, пауза и исчерпанный лимит сохраняются. Новое успешное подключение автоматически доступно всем сотрудникам с активными ключами.

## Переход к настоящему входу

Это проектный контракт будущего сервера MOX, а не уже реализованные endpoints:

| Запрос MOX | Результат |
| --- | --- |
| `POST /api/auth/attempts` | Создать попытку подключения или повторного входа: `attemptId`, `status`, `authUrl`, `expiresAt` |
| `GET /api/auth/attempts/:id` | Получить состояние; при успешной серверной проверке — `connectionId` и публичные сведения об аккаунте |
| `DELETE /api/auth/attempts/:id` | Отменить незавершённую попытку |

Состояния: `pending` → `verifying` → `connected`; альтернативные окончания — `cancelled`, `expired`, `failed`. Создание и чтение попытки требуют сессии администратора и проверки окружения. Повторная доставка результата не должна создавать вторую подписку.

В документированном сценарии Codex app-server вызов `account/login/start` с типом `chatgpt` возвращает `loginId` и `authUrl`. Завершение приходит через `account/login/completed`. После успешного события MOX должен отдельно прочитать аккаунт и проверить его соответствие ожидаемому подключению. [Официальный сценарий входа](https://learn.chatgpt.com/docs/app-server#3-log-in-with-chatgpt-browser-flow).

Для каждой попытки серверу нужен приватный временный профиль авторизации. Существующая авторизация подключения заменяется только после полной проверки результата. Неверный аккаунт или неудачный вход не должны перезаписывать рабочую авторизацию. Только сервер хранит и обновляет секреты; браузер получает публичные сведения и статус попытки.

Документированный `account/read` показывает тип аккаунта, почту и тариф. Источник стабильных ID аккаунта и workspace ещё нужно подтвердить для выбранной версии адаптера; сравнение только почты недостаточно. До такой проверки нельзя объявлять реальную привязку аккаунтов готовой. [Поля аккаунта](https://learn.chatgpt.com/docs/app-server#1-check-auth-state).

Browser flow использует локальный callback app-server. При размещении MOX на удалённом сервере нужно обеспечить поддерживаемый путь callback либо использовать документированный `chatgptDeviceCode` с адресом подтверждения и кодом. Адрес и параметры входа должен возвращать адаптер; MOX не конструирует OAuth URL самостоятельно. [Device-code flow](https://learn.chatgpt.com/docs/app-server#3b-log-in-with-chatgpt-device-code-flow).

В рабочем интерфейсе статус определяется ответом сервера. Сообщение от окна может инициировать обновление статуса, но не подтверждает авторизацию. Закрытое окно также не доказывает, что серверная попытка завершилась: отмена и конкурирующее завершение согласуются на сервере. GitHub Pages обслуживает только статические файлы; для этого контракта требуется отдельный backend.

## Учёт токенов

В прототипе `dist/usage.js` хранит события в памяти и считает расход по сотруднику через все его подключения. Группировка по сотруднику сохраняется при отзыве или замене ключа. Никаких реальных токенов эти значения не отражают.

Периоды — текущие календарные день, неделя и месяц в `Europe/Moscow`. День начинается в 00:00, неделя — в понедельник, месяц — первого числа. Левая граница включена, правая исключена. Дата относится к завершению запроса, а не к моменту открытия страницы. Экран пересчитывает период при возвращении на вкладку и раз в 30 секунд.

Одна запись содержит ID запроса, ID сотрудника и подключения, время завершения и получения, источник и два счётчика: входные и выходные токены. Повторное событие с тем же ID не начисляется снова; конфликтующие значения требуют обработки. Отсутствующий счётчик хранится как `null`. Ноль означает известное нулевое значение. При неполных данных показана известная часть суммы с отметкой `+ ?` и числом таких запросов.

Исходные данные вымышлены. Каждая успешная «Проверка запроса» добавляет 2048 входных и 384 выходных токена владельцу ключа. Простая проверка ключа и отказ до отправки запроса ничего не начисляют. Отзыв ключа сохраняет накопленную историю.

В будущем шлюзе:

- Привязывать запрос к сотруднику после серверной проверки ключа. Не принимать ID сотрудника и расход от клиентского приложения как достоверные.
- Сохранять фактические счётчики ответа провайдера для каждого модельного запроса. Один ход Codex может содержать несколько запросов; суммарные обновления не должны начисляться повторно.
- Хранить ID собственной попытки и ID ответа провайдера; позднее получение счётчиков обновляет исходную запись идемпотентно.
- Различать отказ до отправки, завершение с известным расходом и отправленный запрос без окончательных данных. Ошибка или обрыв после отправки не доказывают нулевой расход.
- Не выводить токены из длины текста, процента квоты или цены подписки. Детальные счётчики кеша и рассуждений не складывать повторно с общими, если они уже входят в них.
- Сохранять события независимо от срока действия ключа. При удалении сотрудника оставлять архивную строку для истории.

Документированный `account/usage/read` даёт агрегаты аккаунта и дневные суммы; он сам по себе не устанавливает расход отдельных сотрудников MOX и разделение входа/выхода. Для персональной таблицы нужен учёт запросов в шлюзе. [Сведения об использовании аккаунта](https://learn.chatgpt.com/docs/app-server#7-token-usage-chatgpt).

## Разделение Fast и обычного режима

Для каждого модельного запроса сохраняются `requestedMode` и `effectiveMode`: `standard`, `fast` или `null`. Первое поле обозначает выбранный режим, второе — подтверждённый результат обработки. Таблица и карточки суммируют входные и выходные токены по `effectiveMode`:

| Результат запроса | Группа в таблице |
| --- | --- |
| Подтверждён обычный режим | Fast выключен |
| Подтверждён Fast | Fast включён |
| Подтверждение отсутствует, в том числе у старой записи | Не подтверждён |

Если запрошен Fast, а подтверждён обычный режим, расход относится к обычному. Положение переключателя само по себе не устанавливает фактический режим. Отсутствие подтверждения режима и отсутствие счётчиков токенов — независимые состояния: известные токены неподтверждённого режима входят в общий расход, а неполный счётчик подтверждённого Fast остаётся в группе Fast.

Смена режима влияет только на следующие запросы, в том числе внутри существующего чата. Ранее записанные значения, ID сотрудника и время завершения сохраняются. Все периоды используют ту же московскую календарную шкалу. Сумма трёх групп равна общему расходу; токены не умножаются на коэффициенты кредитов или стоимости.

В демо после проверки ключа доступен выбор Fast для запроса. В раскрывающемся блоке «Сценарии учёта токенов» можно выбрать подтверждение запрошенного режима, подтверждение обычного режима или отсутствие подтверждения. Каждый успешный запрос добавляет 2048 входных и 384 выходных токена в соответствующую группу.

В рабочем шлюзе подтверждение должно поступать из достоверных данных адаптера провайдера. Поддержку такого подтверждения для настоящих подписок ещё нужно проверить. Отсутствующее или неизвестное значение нельзя автоматически заменять обычным режимом. Позднее подтверждение требует идемпотентного исправления исходной записи с перемещением расхода между группами без увеличения общей суммы. В текущем прототипе такого исправления нет: повторный ID с другими токенами или режимом отклоняется как конфликт.

## Проверено в этой версии

В отдельном Playwright-браузере при 1920×1080: успешный демо-вход, отмена и закрытие окна, блокировка popup, закрытие дочернего окна при обновлении MOX, дубликат аккаунта, неверный аккаунт при повторном входе и сохранение лимита. Существующий ключ после добавления третьей подписки получил доступ к 3 из 3 подключений; три новых чата выбрали их по очереди. У сотрудника прибавилось ровно 6144 входных и 1152 выходных токена. Отзыв сохранил историю и остановил доступ. Сброс восстановил десять сотрудников и две подписки.

Проверены московская полночь, понедельник, переход месяца и года, февраль високосного года, повторные события, архивный сотрудник и неизвестные счётчики. Реальный вход, серверное хранение и сбор фактического расхода пока не реализованы.

Для Fast дополнительно проверены четыре запроса в одном чате: Fast, обычный, запрошенный Fast с подтверждённым обычным режимом и неподтверждённый режим. Получено 4096/768 токенов в обычном режиме, 2048/384 в Fast и 2048/384 без подтверждения. Во всех трёх периодах данные согласованы; изменение переключателя не меняет историю. Проверены конфликты ID при изменении режима, старые записи без режима и независимые неполные счётчики.
